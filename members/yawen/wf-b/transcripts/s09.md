## 1. Filterability metadata

**Legacy behavior and tests.** `FilterableColumn` in `mealie/db/models/_filterable_column.py` marks mapped columns with `info={"filterable": True}`. `QueryFilterBuilder.get_model_and_model_attr_from_attr_string` rejects fields without that marker. In `test_query_filter_builder.py`, tests reject `User.password`, `User.email`, and `LongLiveToken.token`; allow `User.full_name`; and check traversal through relationships, including rejection of `RecipeModel.user.email`.

**Required behavior.** Tortoise filtering and ordering must reject fields that were not marked filterable, including when reached through a relationship. This is a field-authorization rule, not simply “does this ORM field exist?” It must apply consistently to direct filters, nested relationship filters, and sort keys. Existing `IS NULL` / `IS NOT NULL` behavior is separately tested in `test_pagination.py`; filterability must not accidentally make nullable fields inaccessible or change how those operators treat NULL.

**Dependency and isolation.** The metadata is absent from the Tortoise mappings, but adding query-specific filterability metadata to those mappings or maintaining a Tortoise-side allowlist is within Stage 7. Stage 5 supplies the model graph. No later domain operation is needed to resolve the field-policy question.

**Smallest plan revision.** None is necessary. Stage 7 already requires preserving the query language; its implementation should include Tortoise filterability metadata. The acceptance tests can exercise the existing sensitive-field cases against Tortoise model metadata.

## 2. Related `NOT IN`

**Legacy behavior and tests.** `QueryFilterBuilder._get_filter_element` in `mealie/services/query_filter/builder.py` wraps a related `NOT IN` condition in `NOT EXISTS`. Tests include `test_pagination_filter_not_in_m2m`, `test_pagination_filter_not_includes_null`, and `test_pagination_filter_not_in_related_field`.

**Required behavior.** For a related path, exclude a parent if **any** related row has a value in the excluded set—even if that parent also has other nonmatching related rows. Keep a parent with no related rows; the existing empty-category test explicitly requires it. For nullable scalar columns, SQL `NOT IN` retains SQL’s NULL behavior: a NULL value does not satisfy the predicate because the comparison is unknown. That differs from “there is no matching related row,” which includes an empty relationship. Both cases need to be preserved distinctly.

Filtering must not duplicate parents when multiple related rows match, and counts and pagination must count each parent once.

**Dependency and isolation.** This needs Tortoise relationship-path resolution and a correct anti-existence query, but not authentication, recipe writes, or another later application stage. The full legacy pagination test uses repository fixtures and service-created entities, which affects how it is adapted; it does not make the `NOT EXISTS` rule dependent on those later services.

**Smallest plan revision.** None required if Stage 7 includes focused Tortoise-backed cases for both a nullable scalar and an empty/mixed many-to-many relationship. If the full legacy test fixture cannot be adapted within the stage, clarify the test adaptation strategy before implementation rather than weakening expected behavior.

## 3. `CONTAINS ALL`

**Legacy behavior and tests.** `_get_filter_element` implements multi-value `CONTAINS ALL` as an `AND` of separate relationship `EXISTS` conditions. The test `test_pagination_filter_contains_all_m2m` checks that a recipe with both tags matches, recipes with only one tag do not, and the one-value case matches the same recipes as membership. The query-builder JSON test also verifies parsing the operator.

**Required behavior.** Every requested value must be represented among the related rows. Separate `EXISTS` conditions mean a parent can match values held by different rows; one related row cannot satisfy two distinct values. Duplicate association rows must not inflate parent counts or produce duplicate paginated items. For a single requested value, behavior is ordinary membership. For an empty list, the legacy construction’s empty conjunction is true; that edge case should be confirmed and retained if accepted by the existing parser.

**Dependency and isolation.** This requires compiling the operator to multiple correlated existence predicates (or an equivalent Tortoise query). It is Stage 7 query behavior. Stage 5’s association mappings provide the relation graph; no later domain write flow is inherently required.

**Smallest plan revision.** None required. Add the edge-case and duplicate-result checks to the focused Stage 7 verification, without changing expected values.

## 4. To-many sorting

**Legacy behavior and tests.** `QueryFilterBuilder._aggregate_over_relationships` uses a correlated `MIN` for ascending order and `MAX` for descending order. `test_pagination_order_by_to_many_field` asserts those extrema for recipes with multiple tags and puts the recipe with no tags last. `test_pagination_order_by_to_many_field_page_is_not_short` guards against joined rows consuming page slots. `test_pagination_order_by_nulls` checks requested null placement for a nullable to-one relationship.

**Required behavior.** A parent sorts by its lowest related value ascending and highest related value descending. A parent without related rows has a NULL sort value; `order_by_null_position` controls where it appears independently of direction. Related joins must not duplicate parent rows, change the total count, or make a page short. Equal aggregate sort keys have no explicit legacy secondary order, so ties are database-order-dependent; the rewrite should not promise a new deterministic tie-break unless the API contract is intentionally revised. Pagination must still return unique parents and correct totals.

**Dependency and isolation.** Tortoise related ordering may join rows directly, so implementing parity likely requires an aggregate/subquery expression or a two-step query that preserves database pagination. That is a Stage 7 sorting/query concern. The existing test file creates recipes, tags, categories, and foods through legacy repositories, which complicates test adaptation, but Stage 7 can validate the generic semantics using the existing Tortoise model graph and focused fixture records. It does not require converting later recipe write operations.

**Smallest plan revision.** None required for the feature. For test execution, the plan may need a short clarification that unchanged legacy assertions can be exercised through adapted Tortoise database fixtures while service/repository cutovers remain in their later stages. This would clarify the allowed “database-access adaptations”; it would not lower acceptance.
