## Findings

The Stage 6 repository and Stage 7 filter/order implementation already exist and have focused tests. They can be reused; Stage 8 does not need to repeat their general CRUD or query work. The key gaps are **user-specific repository wiring**, a usable async request dependency, and several authentication-specific operations that generic CRUD does not currently cover.

The filter implementation still relies on SQLAlchemy metadata to preserve the legacy filterability and type-conversion rules. Authentication lookups can use ordinary field filters and need not use this query-filter compiler. It remains a dependency for broader repository conversion, but it does not block the Stage 8 user lookup path.

### Login

**Current synchronous chain**

`POST /api/auth/token` → `get_token` in `mealie/routes/auth/auth.py` → `get_auth_provider` → `CredentialsProvider.authenticate` → `AuthProvider.try_get_user` → legacy `get_repositories` / `AllRepositories` → `RepositoryUsers.get_one` and `RepositoryUsers.update`.

The provider updates failed-login counts, lock state and successful-login counts through synchronous repositories. LDAP inherits this provider and also creates/updates users synchronously. OIDC routes call `OpenIDProvider.authenticate`, which synchronously looks up, creates, updates and fetches user profile records.

Relevant files include `auth.py`, `security.py`, `auth_provider.py`, `credentials_provider.py`, `ldap_provider.py`, `openid_provider.py`, `repository_users.py`, `all_repositories.py` and `repository_factory.py`.

**Reusable pieces and minimal wiring**

- `AsyncRepository` provides async get, create, update and delete; transaction-wrapped writes; and relation materialization.
- `User` is already mapped in Tortoise. User lookup needs explicit group, household and long-lived-token relation loading for `PrivateUser` fields.
- Add a user-focused async repository/bundle for user lookup by username/email, updates and user creation. It should use direct Tortoise filters, with case-insensitive matching matching existing `any_case=True` behavior.
- Convert the credentials, LDAP and OIDC provider entry points to async, await repository calls, then make their route handlers await authentication. Password hashing and LDAP/network image work remain synchronous non-database operations; no SQLAlchemy DB calls should remain in these async chains.

### Permissions and authenticated request resolution

**Current synchronous chain**

Protected routers depend on `get_current_user` and often `get_admin_user`. `get_current_user` resolves JWT subjects through legacy `get_repositories(...).users.get_one(...)`; long-lived token claims go through synchronous `validate_long_live_token`, which loads the API token and its user through legacy repositories. `BaseUserController` then uses that resolved user’s group/household identifiers to construct legacy repositories for endpoint work.

**Reusable pieces and minimal wiring**

- Make `get_current_user`, `try_get_current_user`, `is_logged_in` and long-lived-token validation await async user/token repository methods.
- Provide an async request dependency that makes an already-initialized Tortoise connection available to these dependencies and the auth routes. The repository methods perform the async DB I/O; wrapping a legacy `Session` in an async signature would not meet this requirement.
- Keep `get_admin_user`’s current 403 behavior and retain group/household identifiers on the serialized user so existing controller tenant scoping remains intact.
- The household permission-management endpoint and its tests are Stage 9 behavior. Stage 8 covers only authentication-based user/admin permission checks.

### Registration

**Current synchronous chain**

`POST /api/users/register` → `RegistrationController.register_new_user` → `RegistrationService.register_user` → legacy user duplicate checks and invite-token lookup; for a new group, `GroupService.create_group` → `HouseholdService.create_household` plus group/household preference repositories; then user creation, optional food/unit seeding, and invite-token decrement/deletion.

The new-group path calls `SeederService` and legacy ingredient-food/unit seeders. It also dispatches a signup event after registration. All of those operations currently run synchronously.

**Reusable pieces and minimal Stage 9 prerequisite**

- User and invite-token models already exist in Tortoise. Use a registration transaction covering duplicate checks, invite validation/consumption, new group/default household/preferences creation, and user creation. Preserve the existing response model, error statuses/messages and token-use behavior.
- Add only the group/household creation primitives needed to register a user: create group, group preferences and required AI-provider settings; create default or selected household and its preferences; fetch the selected household by group/name; validate and consume an invite.
- Move those registration-only primitives forward from Stage 9. Do **not** move general group/household settings, invitations administration, organizer operations, or their route conversion.
- `seed_data=True` is a further dependency: the existing food/unit seeders are legacy repository-backed. Either provide a narrowly scoped async seed path needed by registration, or record that seeded registration is out of Stage 8 scope and do not claim full registration acceptance. The safer proposal is to include only the async food/unit seeding calls needed by this registration option, while leaving their unrelated CRUD/admin routes for later stages.
- Event dispatch currently happens after the service returns. Keep its timing and payload; database writes should be complete before dispatch, as in the current flow.

### Password reset

**Current synchronous chain**

Forgot-password and reset-password routes instantiate `PasswordResetService`, which uses the legacy repository factory. Token generation does a case-insensitive user lookup and creates a reset-token row. Reset validates the token, reads the user, updates the password and `tokens_valid_after`, confirms the resulting hash, then deletes the reset token. Email delivery is synchronous and happens after token creation.

**Reusable pieces and minimal wiring**

- Tortoise already maps users and password-reset tokens; `AsyncRepository` can handle ordinary CRUD.
- Add user-specific case-insensitive email lookup and password update semantics. Preserve demo-mode restrictions and the `tokens_valid_after` watermark that invalidates earlier sessions.
- Make the service and both route handlers async. Preserve the current transaction/error boundaries: token lookup and password update/deletion should be a single atomic reset operation; forgot-password should keep its existing generic behavior for unknown or LDAP-controlled users and HTTP error when sending email fails.
- Email delivery can remain synchronous, but must not be used to justify synchronous database access.

## Request and test coexistence

Current application lifespan runs legacy `init_db.main()` and scheduler startup, but does not initialize Tortoise. `tortoise_init()` and `tortoise_close()` exist as standalone helpers, while the current `tortoise_connection` fixture initializes an isolated connection only for async unit tests. The application TestClient dependency override currently provides only a SQLAlchemy session.

Proposed Stage 8 test wiring:

1. Keep the legacy `generate_session` override and current `session_context()` fixtures for tests and routes that still use SQLAlchemy.
2. Add an async Tortoise request dependency plus a test-only app lifespan/setup fixture that initializes Tortoise against the same test database and creates/applies the required schema before async endpoint tests run. Close connections through the matching lifespan teardown.
3. Keep the existing session-scoped TestClient pattern if it proves compatible with Tortoise’s event loop ownership; otherwise provide a Stage 8-specific TestClient fixture/client lifecycle for the affected tests. Do not initialize/close Tortoise per request, and do not let pytest’s async fixture loop own connections used by Starlette’s TestClient thread.
4. Leave application-wide production startup cutover, Aerich startup policy, and shutdown conversion to Stage 15. Stage 8’s request wiring must be explicitly opt-in for converted auth/user routes and must not silently redirect legacy repository calls.
5. Retain existing tests and expected values. Add or adapt test database setup only. Convert relevant unit tests to exercise async providers/services directly and keep integration tests on the real async request path. Existing repository fixtures and tests that specifically validate SQLAlchemy can remain operational until their callers’ stages.
